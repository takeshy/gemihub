# Google連携ジョブの障害通知 仕様

## 目的と原則

- Gmailによる予約確認・キャンセル／返金結果・リマインド・問い合わせ返信などのメール送信、およびGoogle Driveへの記事などの同期が失敗した場合に、開発者が状況を把握できるようにする。
- 店主に技術的なエラーを判断させない。一時的な失敗は自動で再試行し、店主には対応が必要な場合、または業務への影響が続く場合だけ、影響と取れる行動を伝える。
- 短時間で復旧した一時的な失敗は、店主にも開発者にも通知しない。
- 既存の再試行回数の上限、ジョブの期限、不要になったリマインドの取り消し処理は変更しない。
- 通常の処理待ちを示す共通警告バナーは復活させない。

## 対象と対象外

対象:

- Gmailによる予約確認、キャンセル・返金結果、リマインド、問い合わせ返信、空き通知、スタッフ招待などのメール送信ジョブ。
- Google Driveへの記事Markdown・記事一覧JSONなどの同期ジョブ（現行の `posts` ジョブ）。
- 上記に必要なGoogle認証情報がない、または失効して処理できない状態。

対象外:

- PayPalの決済・返金そのものと、既存のPayPal滞留アラート。現在の仕組みを維持する。
- 公開処理（`publishConfiguration` / `ensureStorefront`）の既存アラート。現在の仕組みを維持する。
- 審査員店舗のメール記録（`judgeMail`）と、メモリ／デモ環境。実際には送信しないため障害扱いにしない。
- 監査ログの完全性、通知の到達保証（at-least-onceでよく、重複は許容する）。

Drive同期の対象は記事などの永続ジョブとし、公開処理の同期的なDrive書き込みは対象外とする。公開処理を対象に加える場合は、別の仕様変更として扱う。

## 決定事項

レビューで挙げた未決事項は、次の初期値で実装する。値は環境変数で変更できる。

| 項目 | 決定 |
|---|---|
| 開発者通知の送信先 | 汎用HTTPS Webhook（Slack / Google Chat等）。`OPS_WEBHOOK_URL` に設定し、特定サービスへ依存しない |
| 通知先の形式 | 内部の正規化イベントを、通知先ごとのアダプターで変換して送る。`OPS_WEBHOOK_FORMAT=generic\|slack\|google_chat`（初期値 `generic`）。正規化イベントをSlack等へそのままPOSTしない |
| 通知の認証 | `OPS_WEBHOOK_SECRET` がある場合はHMAC-SHA256署名とタイムスタンプを付ける |
| 通知系自体の監視 | Webhookとは別系統で、構造化ログ `ops_notify_failed` のログベース指標、通知アウトボックスの最古未送信の滞留時間、外形監視（`/health` を新設）を使う |
| 403の扱い | HTTPステータスだけで一律に判断せず、Googleのエラー理由で `auth` / `config` / `transient` に分類する。店主へGoogle再接続を案内するのは認証・権限スコープの不足が確認できた場合だけ |
| 障害の再発 | 復旧または対象終了の後に同じ分類の失敗が起きたら、新しい世代のインシデントとして発生通知をやり直す |
| メール送信の閾値 | 初回失敗から5分以上、かつ3回以上の失敗 |
| Drive同期の閾値 | 初回失敗から15分以上、かつ3回以上の失敗 |
| 停滞検知 | メール5分、Drive同期15分、処理可能なジョブの試行が進まない場合 |
| 最終失敗 | 既存の上限に到達した場合、または添付が復旧不能な場合。閾値を待たず初回通知 |
| 設定不備・内部エラー | 初回から通知 |
| 同一障害の要約 | 継続中は6時間ごと。再試行のたびには通知しない |
| 開発者への復旧通知 | 障害発生を通知した場合だけ1回 |
| 店主向けのメール遅延表示 | 30分以上。来店時刻が近い場合は前倒しする |
| 来店時刻が近い場合の前倒し | 予約開始2時間前を切ったら、メール遅延30分を待たずに表示する（初期値） |
| 店主向けのDriveコピー遅延 | ダッシュボードの「要対応」だけに表示し、機能画面には出さない |
| 店主向け表示の範囲 | ダッシュボードの「要対応」と該当機能のローカル表示。全画面バナーは出さない |

環境変数の初期値:

- `OPS_WEBHOOK_URL`: 未設定なら開発者通知は無効。業務処理は通常どおり動く。
- `OPS_WEBHOOK_SECRET`: 任意。設定時は `X-Gemihub-Signature` を付ける。
- `OPS_WEBHOOK_FORMAT=generic`: `generic` / `slack` / `google_chat`。未設定時は `generic`。
- `OPS_MAIL_FAILURE_MINUTES=5`
- `OPS_DRIVE_FAILURE_MINUTES=15`
- `OPS_FAILURE_COUNT=3`
- `OPS_MAIL_STALL_MINUTES=5`
- `OPS_DRIVE_STALL_MINUTES=15`
- `OPS_SUMMARY_HOURS=6`
- `OPS_OWNER_MAIL_DELAY_MINUTES=30`
- `OPS_OWNER_NEAR_VISIT_HOURS=2`

## 状態モデル

通知の有無をジョブの試行回数から推測しない。時間・回数・終了理由を永続化する。

### ジョブの追加項目

現行の `Job`（`server/app.ts`）に次を追加する。

- `mailKind`: `booking_confirmation` / `cancellation` / `refund_result` / `reminder` / `inquiry_reply` / `waitlist` / `staff_invite` など。表示文言と閾値の出し分けに使う。
- `bookingId`, `inquiryId`: 来店時刻の前倒し判定と、機能画面へのリンクに使う。個人情報は持たない。
- `firstFailedAt`, `lastAttemptAt`: 時間判定に使う。
- `lastErrorCode`, `lastErrorClass`: 生の例外文ではなく、許可した分類だけを保存する。
- `terminalReason`: `sent` / `failed_final` / `obsolete` / `unavailable`。
- `incidentId`: 同一障害の集約キー。個人情報やジョブIDを含めない。

### インシデント

`integrationIncident` コレクションを追加する。

- `id`: `${shopId}:${type}:${errorClass}:${generation}`。連携種別と安全な分類、発生世代だけで作り、宛先や本文を含めない。
- `baseKey`: `${shopId}:${type}:${errorClass}`。開いている間の集約と、復旧後の再発判定に使う。最終失敗だけは送れなかったメールごとに `${shopId}:${type}:final:${mailKind}:${inquiryId}`（問い合わせがなければ `job:${jobId}`）とし、別の問い合わせの失敗で表示が上書きされないようにする。この場合の `generation` は発生時刻とし、世代記録を残さない。
- `shopId`, `type` (`mail` / `drive`), `errorClass` (`auth` / `config` / `transient` / `unknown` / `final`), `generation`。
- `openedAt`, `lastFailureAt`, `lastSuccessAt`, `failureCount`, `affectedCount`。`affectedCount` はジョブ単位で数える。ジョブは参加したインシデントを `incidentIds` に持ち、同じインシデントへの再試行・停滞・認証停止では数え直さない。ジョブのない破棄（`shop.google` なし）は1回ごとに1件と数える。
- `terminal`: 既存の上限到達などで再試行が止まった状態。
- `firstNotifiedAt`, `lastNotifiedAt`, `nextSummaryAt`, `status` (`open` / `notified` / `resolved` / `ended`)。
- `resolvedAt`, `resolution` (`succeeded` / `obsolete` / `unavailable` / `archived` / `expired`)。
- 閉じたインシデントは `OPS_INCIDENT_RETENTION_DAYS`（初期値30日）後に削除し、配信ごとの読み取り量を抑える。
- `logId` または `requestId`: 運営者が詳細を確認するための安全な参照。顧客情報を含めない。

`integrationIncidentSeq` に `baseKey` ごとの最終世代を保存する。開いているインシデントがある間は同じ世代へ集約し、復旧・終了後に同じ `baseKey` の失敗が起きたら世代を進めて新しいインシデントを作る。

書き込みは店舗単位のロックまたはFirestoreトランザクションで行い、複数プロセスでも同じインシデントを二重作成しない。

### 通知アウトボックス

`notificationOutbox` コレクションを追加する。

- `id`: `${incidentId}:${event}:${version}`。イベントは `opened` / `summary` / `recovered` / `ended`。
- `incidentId`, `shopId`, `event`, `payload`（下記の許可項目だけ）, `createdAt`, `nextAt`, `attempts`, `status` (`pending` / `sent` / `failed`), `lastErrorCode`。
- 通知専用のワーカーで処理し、メール送信・Drive同期のジョブとは別に再試行する。

## 検知ルール

### 分類

例外そのものではなく、既存の安全なログ情報（`ShopLogs.error` の `status` / `errorCode` / `errorType` / `location`）とHTTPステータスから分類する。

- `auth`: 401、`invalid_grant`、`unauthorized_client`、`insufficient_permissions`、`ACCESS_TOKEN_SCOPE_INSUFFICIENT`、更新トークンなし。店主の再接続で直る可能性がある状態。
- `config`: 入力検証エラー、宛先不正、添付の恒久的な不備、403のAPI無効化・管理ポリシー・請求設定など、店主の再接続では直らない設定不備。
- `transient`: 429、403のレート制限・割り当て超過、5xx、タイムアウト、ネットワークエラー。
- `unknown`: 分類できない内部エラー。403でも理由を特定できない場合はここに入れ、再接続を案内しない。
- `final`: 既存の上限到達、添付の復旧不能、宛先消失など、最終的に送れない状態。送れなかったメールごとの `final` インシデントとし、`errorCode` に原因を残す。原因が認証（`auth`）の場合は、再接続の案内を維持するため共有の `auth` インシデントにも記録する。

`auth` / `config` / `unknown` / `final` は初回から開発者へ通知する。`transient` だけが時間と回数の両方の条件を満たしたときに通知する。

### 403の扱い

- HTTPステータスだけで一律に判断しない。Googleのエラー理由（`errors[].reason` や `response.data.error.status` など）を安全なコードに正規化して分類する。
- 認証・権限スコープの不足（`invalid_grant`、`insufficient_permissions`、`ACCESS_TOKEN_SCOPE_INSUFFICIENT` など）だけを `auth` とし、店主にGoogle再接続を案内できる。
- レート制限・割り当て超過（`rateLimitExceeded`、`userRateLimitExceeded`、`quotaExceeded`、`RESOURCE_EXHAUSTED` など）は `transient` とし、時間と回数の閾値で扱う。
- API無効化・管理ポリシー・請求設定（`SERVICE_DISABLED`、`accessNotConfigured`、`domainPolicy` など）は `config` とし、運営者の設定修正として通知する。店主には再接続を案内しない。
- 理由を特定できない403は `unknown` とし、開発者へ初回通知する。店主にはメール遅延など実際の影響だけを表示する。
- 403の理由やコードは許可した形式に正規化して保存し、生のレスポンス本文は保存・通知しない。

### 時間と回数

- `firstFailedAt` からの経過時間と、失敗回数を別々に判定する。
- 失敗回数は「同じジョブで失敗を観測した回数」とし、経過分数の代用にしない。1分間に複数回flushされる場合や、操作時の再試行があっても時間条件を緩めない。
- 条件はANDとする。5分未満、または3回未満では通知しない。
- 要約は `nextSummaryAt` を過ぎたときだけ作り、再試行のたびには作らない。

### 停滞

- 処理可能なジョブがあるのに `lastAttemptAt` が閾値以上進まない場合を停滞として検知する。
- Google認証がない場合、現行コードは失敗回数を増やさずに戻るため、認証停止として別ルールで検知する。
- `shop.google` がないために `enqueue` が何も保存しない場合も、送信できなかった意図を `blocked` 記録として残し、認証・設定の停止として検知する。無言で破棄しない。
- 審査員店舗、アーカイブ済み店舗、メモリ／デモ環境は対象外とする。

### Drive同期

- `posts` ジョブの失敗を対象にする。
- 成功は実際の同期完了、解消は関連する未処理 `posts` ジョブがなくなったことの両方で判定する。
- 公開処理の同期的なDrive書き込みと `ensureStorefront` は対象外とし、既存の公開アラートを維持する。

### 最終失敗

- 問い合わせ返信の上限（`maxInquiryMailAttempts`）到達、添付の復旧不能、宛先消失など、既存の仕組みが最終的に送信を止めた場合を `final` とする。
- 上限のない通常メールは最終失敗を作らない。閾値と停滞だけで検知する。
- 最終失敗は閾値を待たず、初回から通知する。再試行がないため6時間ごとのまとめは送らない。
- 同じ問い合わせへ同じ種類のメール（返信の送り直しなど）が送れたら `succeeded` で閉じる。それ以外は最後の失敗から `OPS_FINAL_ALERT_DAYS`（初期値7日）で `expired` として閉じ、開発者へは通知しない。
- 店主に表示するのは問い合わせ返信の最終失敗だけとする。その他の最終失敗は再試行していないため「自動で再試行しています」の遅延表示を出さない。
- 公開・復元の処理中に意図的に止めている `posts` ジョブは、停滞として扱わない。

## 開発者向け通知

### 送信経路

- 店主のGmail、障害対象のメール送信キュー、公開処理に依存しない。
- 通知アウトボックス専用のワーカーが `OPS_WEBHOOK_URL` へPOSTする。
- 1回の送信は5秒で打ち切り、業務処理を待たせない。
- 失敗時は指数バックオフ（1分、2分、5分、15分、30分、1時間、以降1時間）で再試行し、状態を保持する。24時間を超えたら構造化ログ `ops_notify_failed` を出し、監視で検知できるようにする。通知は破棄しない。
- Webhookが未設定でも業務処理は通常どおり動く。

### 送信形式

- 内部では正規化イベントだけを作り、通知先の形式へ変換するアダプターを通してからPOSTする。正規化イベントをSlackやGoogle Chatへそのまま送らない。
- `OPS_WEBHOOK_FORMAT` で `generic` / `slack` / `google_chat` を選ぶ。未設定時は `generic`。
- `generic`: 正規化イベントのJSON。
- `slack`: `text` と Block Kit の `blocks`。見出し、店舗、処理、分類、コード、影響件数、継続時間、詳細リンクを含める。
- `google_chat`: Google Chatが受け付ける `text`。長い場合はアダプターで要約・分割する。
- 通知先の文字数上限、エスケープ、リンク形式はアダプター側で処理する。
- 未対応または不正な `OPS_WEBHOOK_FORMAT` は推測して送信しない。通知は `INVALID_FORMAT` として保持し、構造化ログ `ops_notify_invalid_format` で設定ミスを検知できるようにする。
- アダプターは通知先ごとにテストし、正規化イベントの項目が欠けたり、顧客情報が混入したりしないことを確認する。

### 通知内容

許可する項目:

- 環境、店舗ID、障害ID
- 対象処理（メール送信、Drive同期）
- エラー分類・安全なエラーコード
- 発生時刻、継続時間、影響件数、再試行状況
- 運営者向けのリンクまたはログID
- イベント種別（発生、要約、復旧、対象終了）

含めない項目:

- 顧客名、メールアドレス、メール本文、問い合わせ内容
- 認証情報、更新トークン、生の例外文、スタックトレース
- 宛先、添付ファイル名、添付の中身

`payload` は許可項目だけを明示的に組み立て、ジョブや例外をそのままシリアライズしない。

### 重複抑止

- インシデントID（発生世代を含む）とイベント種別・版で通知IDを決める。
- 送信前に `notificationOutbox` の同一IDを確認し、存在すれば作らない。
- 送信後に処理が中断した場合の重複は許容する。受信側がIdempotency-Key（通知ID）に対応していれば抑止できる。
- 同じ障害の再試行ごとに通知を増やさない。継続中は6時間ごとの要約だけを送る。
- 復旧・終了した後に同じ `baseKey` の失敗が再発した場合は、世代を進めた新しいインシデントとして `opened` を送る。通知IDも世代ごとに変わるため、復旧後の再発通知が以前のIDと衝突しない。開いている間の再試行は同じ世代に集約する。

## 店主向け表示

技術的なエラーではなく、確認できた業務上の影響と次の行動を表示する。

- 表示場所はダッシュボードの「要対応」と、該当機能のローカル表示に限る。全画面に警告を出し続けない。
- 表示はインシデントから作る。ジョブの生エラーや内部コードを表示しない。
- メール送信の失敗だけを理由に、予約や決済自体が失敗したとは表示しない。

### 表示条件

- Googleの再接続が必要: `errorClass = auth` で、認証・権限スコープの不足が確認できた場合だけ、遷移せず常に表示する。403のレート制限・API無効化・管理ポリシー・理由不明は再接続を案内しない。
- メール送信の遅延: 初回失敗から30分以上。来店開始2時間前を切った予約に関係する場合は前倒しする。`auth` 以外の403や分類不能なエラーも、実際にメールが遅れていればこの表示を使う。
- 問い合わせ返信の最終失敗: `delivery = failed` になった時点で、その問い合わせ画面とダッシュボードに表示する。
- Driveの保存用コピーの更新遅延: ダッシュボードの「要対応」だけに表示する。
- 短時間で自動復旧し、店主に影響を表示しなかった場合は、表示も復旧通知もしない。

### 文言

- Googleの再接続が必要な場合:
  「Googleとの接続を確認してください。お客様へのメール送信が止まっています。」
  ［Googleに再接続する］
- メール送信の遅延が続く場合:
  「お客様へのメール送信が遅れています。自動で再試行しています。急ぎの連絡は、電話など別の方法でお願いします。」
- 問い合わせ返信が最終的に送れなかった場合:
  「この返信メールを送信できませんでした。返信内容は記録に残っています。宛先と添付ファイルを確認してください。」
- Driveの保存用コピーの更新が遅れている場合:
  「Google Driveへの保存用コピーの更新が遅れています。自動で再試行しています。」

文言は実際に確認できた影響に合わせる。表示は日本語・英語の両方に対応し、既存の `tr()` と `shared/en.json` の方式に従う。

## 復旧と対象終了

- 復旧は、実際の処理成功と、関連する未処理分の解消を確認してから判定する。単にジョブが消えたことだけでは復旧としない。
- キャンセル、期限切れ、アーカイブ、リマインド不要などでジョブが不要になった場合は `ended` / `obsolete` とし、送信成功や復旧とは扱わない。
- アーカイブ済み店舗のインシデントは `archived` で閉じる。
- 開発者へ障害発生を通知した場合は、復旧時にも1回だけ通知する。対象終了は復旧通知と区別し、必要なら `ended` として通知する。
- 店主に影響を表示していた場合は、その表示を復旧状態に更新する。
- 短時間で自動復旧し、店主に影響を表示しなかった場合は通知しない。
- 復旧または対象終了の後に同じ `baseKey` の失敗が再発した場合は、新しい世代の障害として扱い、発生通知をやり直す。復旧通知の有無にかかわらず、再発は新しい障害として記録する。

## 信頼性と障害分離

- 開発者通知の失敗で、予約、決済、業務メール、Drive同期を失敗扱いにしない。
- 通知の記録は業務トランザクションのコミット後に行う。業務トランザクション内で通知をenqueueしない。
- 通知は業務処理と別のキュー・別のワーカーで再試行する。
- 通知先が停止している場合は失敗状態を保持し、ログベース指標・滞留時間・外形監視で検知できるようにする。
- 同じ障害の通知が大量に作られないよう、永続的なIDと共有ストレージ上のロックまたはトランザクションを使う。
- 通知送信後の中断による重複は許容し、通知IDを再利用して受信側の重複抑止に委ねる。
- トークン欠落時は失敗回数を増やさず処理が戻るため、この停止状態も停滞検知の対象にする。

## 既存実装への変更点

- `Job` に目的・参照・失敗時刻・終了理由・インシデントIDを追加する。
- `flushJobs` の成功・失敗・対象終了・最終失敗で `terminalReason` とインシデントを更新する。生の `err.message` は通知・集約に使わない。
- `enqueue` で `shop.google` がない場合に無言で破棄せず、`blocked` 記録を作る。
- 毎分のワーカーに、停滞検知と通知アウトボックスの処理を追加する。通知処理はメール・Driveのロックを保持しない。停滞検知だけは、配信と同じロック（メールはメールロック、Driveは店舗ロック）の中でジョブを読み直して判定する。送信・削除済みのジョブを古い内容で書き戻して再送させたり、復旧済みのインシデントを再オープンしたりしないため。
- 管理画面の「要対応」にインシデントを追加し、該当機能へのリンクを付ける。
- 公開処理・PayPalアラート・既存の再試行上限・リマインド取消は変更しない。
- 運営者向けの詳細リンクは、顧客情報を含まないログIDまたは管理画面の店舗・インシデント参照にする。

## 受け入れ条件

1. 一時的な失敗が閾値前に復旧した場合、店主にも開発者にも通知されない。
2. 継続する送信失敗・同期失敗・認証停止を開発者が把握できる。
3. 同一障害の再試行ごとに通知が増えない。継続中は6時間ごとの要約だけになる。
4. 店主には技術的なエラーではなく、実際の影響と必要な行動が表示される。
5. 通知先の障害が予約・決済・メールの処理に波及しない。
6. ジョブの取り消しや期限切れを、送信成功と誤認しない。
7. 通知やログに顧客情報・認証情報・生の例外文が含まれない。
8. 既存の再試行、問い合わせ返信の送信状態、公開・決済アラートが維持される。
9. 通知系の停止を、通知系とは別の監視で検知できる。
10. 認証欠落で `shop.google` がない場合も、無言で破棄せず停止として検知できる。
11. メール種別ごとに、予約確認・返信・リマインドの影響を正しく表示できる。
12. 来店時刻が近い予約では、メール遅延の店主表示を30分より早められる。
13. 403のレート制限・API無効化・管理ポリシー・理由不明では、店主に一律のGoogle再接続を表示しない。再接続の案内は認証・権限スコープの不足が確認できた場合だけになる。
14. `OPS_WEBHOOK_FORMAT` に応じてgeneric / Slack / Google Chatの形式へ変換され、正規化イベントをそのまま送らない。不正な形式では送信せず、設定ミスを検知できる。
15. 復旧後の再発が新しい世代の障害として通知され、以前の通知IDと衝突しない。

## テスト方針

- `Store(":memory:")` と `createApp` を使い、実時間を待たずに時刻を注入して閾値・停滞・要約を検証する。
- `flushJobs` / 通知ワーカーは純粋な判定関数と副作用に分け、境界値をテストする。
- 一時失敗、閾値前復旧、閾値到達、最終失敗、認証停止、停滞、対象終了、アーカイブを個別に検証する。
- 同一障害の複数ジョブ、再試行、6時間要約、復旧1回、重複通知抑止、復旧後の再発（新しい世代と通知ID）を検証する。
- 401、403の認証理由、403のレート制限、403のAPI無効化・ポリシー、理由不明の403を分類し、店主向けの再接続案内が認証理由だけに限定されることを検証する。
- generic / Slack / Google Chatの変換結果と、不正な `OPS_WEBHOOK_FORMAT` で送信しないことを検証する。
- Webhook失敗時に業務処理が成功したままであること、未送信が保持されること、`ops_notify_failed` が出ることを検証する。
- 通知payloadに顧客情報・メールアドレス・本文・トークン・生の例外文が含まれないことを検証する。
- 既存の `tests/booking-mail.test.ts`、`tests/inquiries.test.ts`、`tests/operation-locks.test.ts`、`tests/booking-reminders.test.ts` の挙動が変わらないことを確認する。

## 残る実装時の決定

- Webhookの具体的なサービス（Slack / Google Chat / その他）とチャンネル。形式は `OPS_WEBHOOK_FORMAT` のアダプターで対応する。
- 監視の具体設定（ログベース指標のしきい値、滞留時間のアラート値、外形監視の間隔）。
- 来店時刻が近い場合の前倒し時間（初期値は2時間前）を運用上そのまま採用するか。
