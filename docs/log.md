# Update Log

## 2026-09-05
* **Update**: The Gemini API key password is now asked once per session instead of once per page load. Unlocking already stored the decrypted key in the 30-day session cookie, but the browser kept its own copy in memory only, so free-plan chat and local workflow execution re-prompted after every reload. `ensureCachedApiKey` (`api-key-cache.ts`) refills that copy from the session via the new same-origin `GET /api/auth/api-key`, and chat, `useLocalWorkflowExecution`, the `command` node fallback in `local-executor`, and the IDE page load all use it before falling back to the prompt. Nothing new is persisted and a locked session still prompts (`features/chat.md`).
* **Update**: Selecting Vertex AI in Settings > General is now "Vertex only". A stored Gemini API key is kept but ignored on every AI path for a Drive-mount user with `usePersonalVertex`: `/api/chat` without `projectId` reads settings and dispatches to the personal route (so plugin `api.gemini.chat` runs on Vertex), workflow `command` nodes are delegated by `local-executor` to `POST /api/workflow/execute-node` (which now accepts `command` only in that mode) with no API-key unlock prompt, `execute-full` and scheduled runs set `ServiceContext.personalVertex` (replacing `personalVertexBilling`; the own-project source now works unattended), and AI workflow / `.base` generation gained `personalVertexAction` entry points. Tenant, billing, model allow-list, and the 15-round tool cap are resolved in one place, `app/services/ai/personal-vertex.server.ts` (`architecture/mounts.md`, `architecture/premium.md`).
* **Update**: "My Google Cloud project" (personal Vertex AI on the Drive mount) now requires the user's own OAuth client JSON, like the desktop app. Settings > General > Vertex AI gained an "Upload OAuth client JSON" step (Web application client, redirect URI `/auth/vertex/callback`); "Connect with Google" is enabled only once a client is stored, and `/auth/vertex/start?personal=1` rejects a personal connection without one, so the service-wide OAuth client is never used to mint tokens for a project the service does not own. `POST /api/personal-vertex/connection` stores the client (`users/{uid}.vertexOAuthClient`, encrypted) and the org/service route shares the same validation (`parseVertexOAuthClientInput`). The execution project ID is prefilled from the JSON when empty (`architecture/mounts.md`).

## 2026-09-04
* **Fix**: `renameFileLocal` on a file that already existed on Drive only rewrote the IndexedDB cache and cached remote meta. Push never sends names and background polling rewrote the cached meta from Drive, so Kanban card renames, Secret Manager moves, and dashboard renames silently reverted within one poll. Real ids now rename on Drive immediately through the same `bulkRename` + meta-mirror path the file tree and chat tools use; `new:` placeholders keep the cache-only behaviour (`features/sync.md`).
* **Fix**: An incremental Pull that skipped a download (binary on mobile, file over 20 MB) still recorded the new checksum but left the stale cached copy in place; since reads trust the cache, the old bytes were shown indefinitely. The stale copy is now deleted so the file lazy-fetches on next open, matching Full Pull. A pull that only carried a remote rename now also updates the cache record's `fileName`.
* **Fix**: Queued soft deletions whose Drive file was edited on another device were invisible in the Pull badge and dialog (pending-deleted ids are filtered from the cached remote meta) yet still rejected Push with "Pull first". Polling and Push now cancel such reservations, the file re-enters the tree as a pending pull, and a toast names it.
* **Fix**: The Push dialog listed only modified/new files while the badge also counted queued deletions; opening the dialog then "corrected" the badge down and could disable the button with deletions still pending. Deletions are listed as trash rows with a diff of the Drive content being removed.
* **Fix**: Local sync meta is patched as a delta inside one IndexedDB transaction (`patchLocalSyncMeta`) by polling and Pull instead of writing back a snapshot read before per-file cache reads or downloads — a `new:` → Drive migration finishing in between lost its entry and was re-registered as uncached.
* **Fix**: "Reload from Drive" (`forceRefresh`) discarded the cached content but kept the local edit history, leaving the file flagged as modified with a diff that no longer matched.
* **Fix**: `GET /api/sync` reconciliation only dropped meta entries whose Drive file was gone; root files that exist on Drive but are missing from `_sync-meta.json` (an external client crashed between uploading and writing the meta) stayed invisible to Push/Pull until the user ran "Detect untracked files". They are now registered during reconciliation (`addUntrackedFilesToSyncMeta`), mirroring how the Desktop plugin self-heals (`features/sync.md`).
* **Update**: Full Push skips clean files whose last-synced checksum still matches Drive (re-uploading identical bytes bumped `modifiedTime` and showed up as a pull everywhere else) and no longer copies system files into local sync meta. `_sync-meta.json` rebuilds and bulk renames preserve `publicPath`. `GET /api/sync` performs one meta lookup instead of two, remote-change polling also runs on tab focus and reconnect, and the push/pull badge recomputation is debounced. Docs corrected (20 MB cache threshold, Full Pull no longer sends `skipHashes`, `syncMetaFileId` is informational).

## 2026-08-22
* **Fix**: `/public/file/:fileId/:fileName` served ANY Drive file id from the app's own origin with no CSP, while every sibling proxy route (`api.storage.read`, `api.temp-edit`, `drive-compat`) sandboxes its output. A third party could publish their own HTML on Drive and have it execute on this origin — reaching the IDE's IndexedDB cache (every cached file, edit history, encrypted settings) and `/api/*` with the viewer's cookies. Public links are now signed (`public-link.server.ts`, HMAC over the file id keyed by `SESSION_SECRET`, stored as `publicPath` in `_sync-meta.json` and minted on demand by `action: "publicLink"` for older published files), every response carries a sandbox CSP plus `nosniff`, and an unsigned request for script-capable content (`.html`, `.htm`, `.js`, `.mjs`, `.svg`) is refused with a 403 that asks for a re-publish. Unsigned passive content (images, PDF, CSS, text) still serves, so images baked into already-published pages keep working. Publishing remains anonymous-readable — the signature proves GemiHub minted the link, it does not authenticate the viewer (`architecture/utils.md`).
* **New**: The sync bar warns when unpushed local edits have been sitting for more than 7 days. `editHistory` in IndexedDB is the only record that a file changed locally, so losing that store (storage eviction, ITP, "clear site data") makes the edits invisible to Push and lets the next Pull overwrite them (`features/sync.md`).
* **Update**: Plugins can no longer reach credential-bearing files through `api.drive` — `settings.json` and `_encrypted-auth.json` (which carry `encryptedApiKey`, `encryptedPrivateKey`, and the PBKDF2 salt), `plugins/**` (another plugin's code), and `_sync-meta.json` are filtered from reads, writes, listings, and searches, id-addressed calls included (`plugin-file-guard.ts`). `PluginAPI` already exposed no decrypted key material; a test now pins that surface so a future member cannot quietly add it. This is an API boundary, not a sandbox — plugins share the page's realm, and real isolation would mean moving them out of it (`integrations/plugins.md`).
* **New**: The dashboard and Launcher calendar can explicitly reflect Google Calendar events for the visible month. Results are read-only, cached per month in browser IndexedDB, and restored after switching files or reopening the calendar without an automatic network request (`features/dashboard.md`).
* **Update**: Clicking a calendar date now opens a compact day-detail modal instead of expanding the calendar. The redundant date/no-events block is gone, the header keeps only Add event, and Escape closes the day modal without also closing its parent Launcher (`features/dashboard.md`).
* **Fix**: Deleting a dashboard now cancels its pending debounced save and waits for an in-flight save before removing the latest file id, preventing a deleted dashboard from being recreated from stale local cache (`features/dashboard.md`).

## 2026-08-21
* **Fix**: The Business cancellation lifecycle had four holes. (1) The owner-protection check ran before the super-admin check and did not exempt it, so no one — not even a service administrator — could remove or demote an owner while a contract was active, and the documented "transfer to another Owner" path does not exist (there is no self-service Stripe transfer); the check is now a single super-admin gate whose message names the two real options. (2) `accountStatus: "disabled"` was never consulted on the project mount, so an administratively closed account kept a fully writable organization; access is now decided by one helper, `organizationLifecycle()`. (3) `deleteAfter` was only stored, never evaluated — a canceled organization stayed readable forever; past the window the lifecycle is `expired` and the API answers 403 while the data waits for a service administrator to delete it (deliberately manual; the admin console now shows each account's lifecycle and deadline). (4) `setAccountBillingStatus` wrote blindly, so a `past_due` webhook cleared the cancellation fields while leaving the account disabled; it now runs in a transaction that only re-enables an account it is bringing out of `canceled`, and a redelivered cancellation cannot extend the export window (`architecture/mounts.md`, `architecture/premium.md`).
* **Fix**: A read-only organization refused AI with `ModelNotAllowedError` ("that model is not allowed here") and refused storage writes with a bare `Error` (a 500 on most routes).
