# omaiweb 仕様書

## 想定しているsystem
backend: Golang
frontend: React
infra: Google Cloud,Firestore, Google Drive
tool: Storybook, terraform

WPAで作成したい。
各画面はStorybookで確認できるようにしたい
Storybook の画面は「はじめる」「お店づくり」「運営」「お客様の予約」「ブログ・お知らせ」「カレンダー連携」「使い方」のカテゴリに分類する。予約画面では指名・指名なしの選択、Calendar 連携では未連携・連携中・家族本人・担当者削除後を確認できるようにする
基本的にデータはGoogle Driveに保存して、このサービスが終了したとしてもデータを失わないようにしたい(非ベンダーロック)
ただし、token情報などはFireStoreで管理する

## 作るもの

小さなお店（美容室、ネイルサロン、エステ、整体、個人レッスンなど、予約で回る個人商店）のための、自店専用の予約システムを、店主との対話から作るサービス。

- 店主は技術者ではない。画面には「お店の情報」「内容を確認」「仮公開」「本番公開」などの分かりやすい言葉を使い、内部の設定や専門用語を見せない
- 始まりは Google ログインだけ。面倒な初期設定や専門用語を店主に見せない
- データ（予約やお客さんの情報）は店主の Google ドライブのスプレッドシートに残り、店主がいつでも開いて見られる。仕様書（spec.md）と変更の履歴（history.md）も店主の手元に残る
- お金の機能（決済や予約金）は入れない。無断キャンセルへの対策も入れない（キャンセルされたことは記録に残す）

## どの段階でも守ること（利用者から見た約束）

- ページ構成・見た目を本番に反映する前には差分を見せ、店主が画面で反映を選んでから変える。本番データ（メニュー・料金、勤務、営業時間・予約ルール、記事）は各管理メニューの「保存」で反映する。声だけで本番への反映や保存を承認したことにしない
- お客さんには自分の予約だけが見える。他人の予約は一切見えない
- 招待されていない人は運営の画面に入れない。招待されても、受け入れるまでは運営できない
- 予約のキャンセルは記録を消すのではなく、「キャンセル」に印を付けて残す
- 本番公開の前に仮公開できる。仮公開したページは、ページを用意した本人が同じGoogleアカウントでログインしている場合だけ表示する。初回作成前の独立したプレビューは設けず、仮公開した内容を本番公開前にプレビューで確認する。画面編集内の練習操作は引き続き本番データに反映しない
- 変更したら、その記録が履歴に残り、あとから追える

## 段階

### 初回の確認・仮公開・本番公開

- 初回は文章・音声で用意したい機能を相談し、確認画面から「仮公開する」で直接進める。「承認済み」の中間画面と「項目ごとに入力・修正」「この内容で進む」は設けない
- 確認画面は「下記の画面でいいですか？」とし、予約・お店のこと・マイページ・お問い合わせ・ブログ一覧と記事・お知らせ一覧と記事・追加ページを、実際の表示を縮小したサムネイルの一覧で示す。内容は仮の案と明示し、「画面ごとの細かいデザイン調整は仮公開後に画面単位で行えます」と説明する。機能の流れはアイコンと矢印でも図解する
- スタッフ・メニュー・料金・営業時間などの各種設定は、仮公開後に各設定メニューで行う。初回専用の一括設定・再承認画面には進めない。「保存」は仮公開中なら仮公開の内容を更新する
- 仮公開したページは、そのページを用意した本人のGoogleアカウントのログインに限定する。ほかのお客様や招待メンバーも閲覧できない。制限は追加ページ・ブログやお知らせ・画像・空き枠・予約や問い合わせのAPIとHTMLにも適用し、独自ドメインでも同じ条件にする。仮公開のHTMLは共有キャッシュさせず、Cookieによる区別と検索除外のヘッダーを付ける
- 仮公開中は「画面の確認・本番公開」を開き、保存済みの各画面を切り替えて確認できる。操作はサンプルのお客様と予約を使い、実際の予約やメールは変更しない。プレビューは本人だけに許可する
- プレビューに「本番公開する」を置き、本人限定の閲覧制限を解除する。プレビューの版と設定・記事のハッシュをサーバーで照合し、その後に内容が変わった場合は読み直して再確認してもらう。本番公開後も、自分の予約の閲覧や予約操作にはお客様のログインが必要
- デザインは「画面を試す・編集」で各画面を更新し、全体的な表示や機能の修正は「AIとお店をつくる」で行うと案内する。仮公開の反映を再試行しても二重に公開処理や履歴が増えない

### Stage 1：現在のお店の設定・履歴とAI相談

- 「AIとお店をつくる」に現在のお店の設定をインフォグラフィックで表示する。独立した「お店の仕組み図」メニューは置かない。メニューと料金・所要時間、スタッフと勤務・対応メニュー、営業時間・休日、受付・キャンセル条件、指名・指名なしの予約の流れ、公開ページを図解する
- 「データとファイル」の独立した欄は置かない。変更履歴と現在のお店の設定は画面内で確認する。ダウンロードボタンは設けない。「データと権限の仕組み」でデータの流れ、各シートと専用管理メニューの対応、公開・非公開の保存先、閲覧権限を図解し、店主の台帳・Drive へのリンクも同じ欄に置く。初回の依頼画面と確認画面には表示しない。確認後は中間画面を挟まず仮公開し、仮公開中であることと各画面の編集・各種設定・画面の確認・本番公開への導線を示す
- 「データ管理」は店主専用とし、予約・お客様・メニュー等の標準シートは各専用画面に誘導する。専用画面のない追加シートを一覧・検索・行追加・編集できる。シートはスプレッドシート側で追加し、1行目を重複のない列名（100列まで）、2行目以降をデータ（1000行まで）とする。列名・列順・既存の計算式は維持し、変更したセルだけ RAW で保存する。行全体の削除は提供しない。保存時に編集元と比較し、競合時は編集を保持して停止する。固定した行への再試行で二重追加を防ぐ
- 「画像管理」は店主専用で、アップロード画像・既存のメニュー画像・Gemini生成画像を同じ一覧で検索・名前変更・削除できる。画像は店主の Drive、参照と生成の記録はサーバーで管理する。登録時の使用画面の指定は不要で、現在使用している画面名を一覧に表示する。文章・音声・ペンの依頼とAIページ作成では管理画像をpickerから5枚まで・合計10MB以内で選び、画像の実データとIDをモデルへ渡す。選択していない新規の管理画像IDを提案に含めることは拒否する。ヘッダー・追加ページ・メニューの編集欄からも画像を選び、ローカル確認と保存・本番反映の後に公開する。公開中に参照する画像だけ配信し、CRM 添付や他店舗の画像を参照できない。使用中の画像の削除は拒否し、一覧からの削除でも Drive 本体は保持する
- お客様メモの画像は、お客様ごとの詳細画面の「画像一覧」で確認する。画像管理にはお客様メモのタブや全顧客のメモ画像一覧を置かない。管理画像や依頼のpickerに含めず、AIへ渡さない。非公開画像の閲覧・編集権限は既存のお客様詳細画面に従う。
- 画像管理の「AIで生成」は、お店づくりと同じ依頼方法のカードで「文章で依頼／音声で依頼」を選んだ後、指示・名前・比率・任意の参考画像を受け付ける。文章では入力欄、音声では録音ボタンと確認・修正欄を表示する。「生成して結果を確認」の後は画像を表示し、「さらに依頼する」で生成画像を参考に修正を依頼し、「これでOK」で一覧に戻る。音声認識した文字を指示欄で確認してから、Gemini の画像生成 API を呼ぶ。生成画像も同じ一覧に保存する。生成の重複防止と Drive 保存の再開に対応し、予約操作を画像生成の完了待ちにしない。文字・音声の指示だけでページの公開内容は変更しない
- 同じ画面の先頭に変更履歴を新しい順で表示し、その下に現在のお店の設定と AI への相談を並べる。保存・公開後は設定と履歴を更新する。画面を開くと現在の内容を取得する。現在のお店の設定にはシートを直接編集した設定も反映する。仕様・履歴を確認するだけでは設定は変更しない
- 「はじめる」でAIの質問に答える。文章入力を基本とし、「音声入力」でモーダルを開き、話した内容を書き起こす。モーダル内の文章を編集でき、下書きはチャットの入力欄にも保持する。終了キーワードの案内と変更設定はモーダル内にだけ表示する。Escape・閉じる・下書きに戻るで音声認識を止め、未送信の文章を保持する。末尾で「以上」と言うとキーワードを除いて送信する。AIの返答は画面で確認する。初回は機能図と各画面のサムネイルを確認して「仮公開する」を押し、本人限定のページを直接用意する。既存店の変更は「このように変更してよいですか？」とし、「変更内容を反映する」で現在の公開範囲を維持して反映する。質問への回答もチャットに表示し、そのまま次のメッセージを送れるようにする。文字・音声の会話には直前のやりとり・現在の設定・履歴を渡し、不明な事実は捏造しない。
- 質問への回答では変更プランを作らない。変更依頼は不明点を相談し、変更プランの作成→確認・承認→仮公開または変更の反映へ同じ画面で進める。会話や質問だけで本番を変更しない。文字相談・変更プランでは表示中の仕様の世代と内容を照合し、変更されていたら更新を促す
- 仕様と履歴は運営メンバーに限定し、変更プランの作成・音声入力は店主のみ利用できる。初回のお店づくりは従来の聞き取りからプラン確認へ進める。「どんなお店をつくりますか？」の聞き取りは承認前だけ表示し、確認画面の「仮公開する」で直接仮公開へ進む

### Stage 2：画面を試し、ローカルで編集して反映する
店主が実際のお客様向け画面をサンプルで試し、ペンや項目入力で変更してから本番へ反映できる。

- 運営メニューに「画面を試す・編集」を置く。対象はお客様向けの予約、お店のこと、マイページ、お問い合わせ、ブログ一覧・記事、お知らせ一覧・記事と、ユーザーが追加したページ。ログイン後の初期表示をこの画面にし、サイドメニュー「画面を試す・編集」の配下に「共通パーツ」「予約・お店の情報」「ブログ・お知らせ」「追加ページ」のツリーを置く。他の管理メニューを開いてもツリーは保持する。店主以外は予約管理を初期表示とする。管理画面にはペン入力を付けず、各管理画面共通の「公開ページを開いてペンで変更を依頼」は表示しない
- 本体と同じお客様向け画面を、専用のモック API とサンプルデータで動かす。練習用の予約・キャンセル・問い合わせはモック内だけで完結し、本番の台帳、メール送信、Google Calendar には接続しない
- 現在の画面のプレビューを最初に表示し、「YOUR SHOP, YOUR WORDS」「試して、直して、反映する」などの共通見出しは試す画面には出さない。共通の「お店の情報をローカルで編集」フォームは設けず、お店の基本情報は管理メニューの保存で本番へ反映する。ページ本文の編集とサンプルデータの編集はプレビューの下に折りたたむ。変更がある場合だけ「反映する」「変更を取り消す」を表示する。料金・勤務・営業時間・予約ルールは専用管理メニューで保存し、ページ反映の対象には含めない。サンプルのお客様名・予約・記事も編集できる。サンプルデータは本番への反映対象に含めない
- 編集内容はログイン中のアカウントとお店ごとに、このブラウザの localStorage に保存し、画面を閉じても復元する。端末間では共有せず、サイトデータを消すと未反映の編集は失われる。保存に失敗した場合は未保存と分かる表示にし、反映を許可しない
- ツリーの状態ラベルは変更がある項目だけ「変更あり」を表示する。変更なし・取得済み・未取得・確認中のラベルは表示せず、キャッシュの有無は利用者に意識させない。競合は色・補助説明と開いた際の比較画面で区別する。状態確認は初期表示・30秒ごと・ウィンドウへ戻った時にメタデータだけで行い、未取得・リモート更新の画面は開くと自動でその本文だけを取り込む。取得ボタンは置かない。ローカル編集があれば上書きせず競合を解決する。「変更を取り消す」は確認後に選択した画面だけをリモートへ戻す
- ヘッダー・フッターは共通パーツとしてツリーから別々に選択し、項目入力またはペンで編集・個別反映できる。他のパーツやページの編集中の内容は反映しない。各画面のコンパクトなツールバーには画面名、変更時のみ状態、ペン入力、表示メニューを置く。ヘッダー・フッターは編集プレビューで初期状態を非表示とし、「表示」で画面ごとに一時的に切り替えられる。共通パーツ自体の編集では選択したパーツを表示する。表示切替は編集プレビュー内だけに適用し、本番の設定・ファイルやローカルの編集データには保存しない
- 画面の修正は「画面を試す・編集」に一本化し、仮公開・本番公開のページには修正ボタンを設けない。試す画面をペンで囲んで、文字・音声で変更を依頼できる。対象が曖昧な場合は候補から店主が選ぶ。対象は店名・紹介文・アクセス・ページ本文・色・配置・紹介画像・共通ヘッダー・フッター。料金・所要時間・勤務・予約ルールはそれぞれの管理メニューで編集する
- ペンによる変更案はまずローカルのお店の情報に反映し、試す画面ですぐ確認する。この時点では本番の設定・公開ページは変えず、公開用プランも作らない。AI による対象確認・変更提案では、画面の画像と変更対象の設定をサーバーに送る
- 新規ページの作成も「AIとお店をつくる」に統一し、独立した「ページをつくる」メニューは置かない。最初に「相談」「修正」「新ページ作成」を選び、その後に「はじめる」を押し、AIの質問に文章または「音声入力」の書き起こしで答える。相談は回答だけを返し、変更プランを作らない。新ページ作成は本文とお客様向けメニュー名をまとめて提案し、確認・反映後に画面ツリーと公開メニューへ追加する。追加後の細かい編集は画面単位で行う。
- 本番へ反映するときは変更一覧と変更前後を表示する。選んだ追加ページ1つの追加・更新・削除だけを反映し、他のローカルページやデータは含めない。店名など全画面共通の変更は共通設定として反映する。公開前の店では先に共通設定を反映する。「この内容を本番に反映」の画面操作を最終確認として、プラン作成・承認・公開を実行する。仕様書と履歴も更新する
- 選択したページの編集元と本番を照合し、同じページが他の操作で変わっていたら上書きせず停止する。無関係なページや料金の更新はそのまま保持する。反映後も他ページのローカル編集と、それぞれの編集元を保持して競合を検出する。シートを直接編集した場合も元の設定との比較で検出する。ローカル編集は保持し、取り込み直して変更を確認できる
- 反映処理の識別子とプラン ID はリクエスト前後にブラウザへ保存する。通信失敗時には同じ操作として再試行し、二重公開・履歴の重複を防ぐ。反映途中は編集を止め、完了するか、サーバー側の状態を確認して編集に戻す
- 終了条件：画面選択→サンプル編集→練習操作、ローカル編集→再読込で復元、ペン→対象確認→ローカル変更→差分確認→本番反映を確認する。反映前に本番が変わらないこと、サンプルが本番へ混入しないこと、競合で上書きしないこと、失敗時に編集を保持し再試行できることを確認する

### Stage 3：会話で聞き取り、プランが出る
店主が質問に答えていくと、お店の情報が揃って、作るもののプランが出る。中心の体験。

- フォームに書き込むのではなく、会話で進める。システムが質問し、店主が答えると内容が項目に整理され、足りないところは続けて質問する
- 初めに聞くこと：どのような業種のお店で、どのようなページや機能を用意したいか。スタッフ・料金・営業時間・予約の決まりなどは、仮公開したあとで入力・確認する。初回から具体値をすべて揃えることは求めない
- 聞き取った内容は画面に一覧で見え、その場で直せる。会話の中に隠れたままにしない
- 揃ったらプランを見せる。プランは「作るものの一覧」（お店のページ、予約の仕組み、運営の画面、お知らせ）をやさしい言葉で示す。店主はその場で注文を言い直せる。了承したら「仮公開する」で本人だけが見られるページを表示できる
- 終了条件：会話で用意する機能を相談し、確認図を見る→了承する→仮公開まで進める。詳しい設定は各メニューで更新し、本番公開前にプレビューで確認する

### Stage 4：お客さんが予約する
お客さんがページを見て予約でき、店主の一覧にその予約が出る。

- お客さんが見られるもの：お店のページ（メニュー、スタッフ、営業時間、行き方）、予約（メニュー・スタッフ・日時を選ぶ）、自分の予約の確認とキャンセル、問い合わせ
- お客さんが予約画面で「指名なし（空いているスタッフ）」または担当スタッフ名を選べる。最初は「指名なし」を選択し、そのメニューに対応するスタッフだけを選択肢に出す
  - 指名する：指定されたスタッフが空いている時間だけ予約できる。指定先が埋まっていても別のスタッフへ自動で変更しない
  - 指名なし：対応するスタッフの誰か1人でも空いていれば予約できる。予約確定直前に空きを再確認して実際の担当者を割り当て、台帳に記録する
- 指名の有無は常にお客さんが選び、店主側に予約方式の切り替え設定は設けない
- メニュー・担当者・日時を変更したら選択済みの予約時間を解除し、空き枠を取得し直す。メニュー変更後も「指名なし」は維持し、選択していた担当者が非対応なら指名なしに戻す。予約内容の確認欄にも指名の有無を表示する
- 休みの日には予約が入らない。いっぱいの時間には重ねて予約が入らない
- 家族・スタッフが Google Calendar を連携している場合は、その人の「予定あり」の時間も予約できない時間として扱う（連携方法は Stage 6）。空き枠の表示時と予約確定直前に確認する。「指名なし」では予定のある人を除き、別の対応可能なスタッフが空いていれば予約できる
- 予約が入ったら、店主の運営画面の予約一覧（日ごと・スタッフごと）に出る。お客さんがキャンセルしたら、一覧でもキャンセルと分かる（記録は消さない）
- 終了条件：同じ予約画面で指名／指名なしを切り替えて予約→店主の一覧に出る→キャンセル、までができる。休みの日に予約できず、満員の時間に重ねて予約できない

### Stage 5：台帳が店主の手元に残る
予約やお店の情報が、店主の Google ドライブのスプレッドシートに残る。

- 予約が入ると、店主のスプレッドシート（予約台帳）に1件として記録される
- メニューやスタッフなどのお店の情報もスプレッドシートにあり、店主がシートを直接開いて直したら、その内容がページや予約に反映される
- お店の仕様書（spec.md）と履歴（history.md）も店主のドライブに置かれ、開いて読める
- Drive の公開成果物はフォルダーごとダウンロードし、web/index.html をダブルクリックするだけで店舗・メニュー・予約画面を表示できる。ビルド済みJavaScript/CSSはこのHTMLにインライン化し、モックの店舗設定・プレビュー用お客様・空の予約と問い合わせ・mode=mock・writes=discarded は別ファイル web/data.js の window.__OMAIWEB_MOCK__ で公開する。HTMLは ./data.js を相対参照し、描画データはそれを正とする
- web/shop.json と web/mock.json は閲覧・外部ツール用に同じ生成元から残す。ユーザーの文字列は安全にエスケープする。予約・問い合わせはブラウザ内の練習だけで、ファイル・サーバーには書き込まない。data.jsを編集すればHTMLを書き換えず表示を変更できる
- 起動は file:// かつ有効な window.__OMAIWEB_MOCK__ が存在するときだけモックAPIを使用する。data.jsがなければエラーで落とさず既存の静的フォールバックを残す。HTTP/HTTPSではグローバルの有無にかかわらずサーバーAPIを使う。配信用distのシェルにはdata.js参照を加えず、admin/index.htmlは対象外とする
- 終了条件：店主がスプレッドシートを開いて予約とお店の情報を確認でき、シートで直した内容が画面に反映される。成果物を実際にfile://で開き、予約操作の破棄・data.js編集での表示変更・data.jsなしの静的表示・HTTP時の二重ガードを確認する

### Stage 6：家族やスタッフを招待する
家族経営のお店で、店主以外の人も運営できるようにする。

- 店主が家族やスタッフをメールで招待できる。相手が受け入れたら、その人も運営の画面（予約一覧、キャンセル対応、問い合わせへの返信）が使える
- 招待の記録（誰を招待して、受け入れたかどうか）は店主のスプレッドシートに残り、店主が開いて確認・修正できる
- 受け入れる前は運営の画面に入れない。お客さんには自分の予約だけが見え、他人の予約は見えない
- お店のデータの置き場所は店主のドライブのまま。招待してもデータが相手に移ることはない
- 終了条件：招待する→受け入れる→運営できる、までができる。招待されていない人、受け入れていない人が運営の画面に入れない

#### 家族・スタッフ各自の Google Calendar 連携

- 店主と参加済みのメンバーは、「家族・スタッフ」画面で自分の Google アカウントを接続し、自分に対応する予約の担当者を選べる。お店を公開した後に利用できる。招待中・参加解除済みの人は利用できない
- 連携はお店ごとに管理し、1アカウントにつき1担当者、1担当者につき1アカウントとする。他のメンバーが連携済みの担当者には接続できない。本人が再接続して担当者を変更できる
- 接続には本人の同意が必要。ログイン中と異なる Google アカウントでの接続は拒否する。OAuth の処理は開始した本人・お店・担当者に紐づけ、有効期限と一度限りの state、Cookie、PKCE で検証する
- 対象は各自のメインカレンダー。「予定あり」の時間帯だけを FreeBusy API で参照し、予約枠と重なる時間を除外する。終日・繰り返し予定も Google が返す時間帯に従う。「予定なし」の予定は予約を妨げない。追加・共有カレンダーの選択、予約のカレンダーへの書き込みは対象外
- 営業時間・勤務時間・休業日・既存予約の制約と合わせて空き枠を判定する。時刻は日本時間を基準とし、予定の終了時刻と予約の開始時刻が一致する場合は重複とみなさない
- 予定の件名・本文は取得しない。取得した予定ありの時間帯も保存・公開せず、空き枠の判定にだけ使う。Calendar 用の更新トークンは暗号化して Firestore に保存し、ブラウザや他のメンバーには渡さない。店主の Drive・Gmail 用トークンとは別に管理する
- Google の空き状況を取得できない場合は、空いていると判断しない。該当担当者を候補に含む空き枠検索・予約確定を一時停止し、HTTP 503 と再接続を依頼する案内を返す。本人が再接続した後に再試行できる
- 本人が連携を解除すると、保存した Calendar 用トークンを削除して参照を停止する。店主が参加を解除した場合も削除し、参加権限のないメンバーの連携は空き判定に使わない。Google 側のアプリ許可そのものの取消は Google アカウントの設定で行う
- 運用設定：Google Cloud で Google Calendar API を有効化し、OAuth 同意画面に `https://www.googleapis.com/auth/calendar.freebusy` を追加する。既存のクライアント ID・シークレットと `/auth/google/callback` を使用する
- 制約：Google Calendar の変更と予約確定は原子的には処理できない。予約確定直前の確認後に Google 側へ追加された予定との競合までは防げない
- 受け入れ条件：本人による接続・再接続・解除、異なるアカウントでの接続拒否、担当者の重複連携拒否、店舗間の分離、終日予定と時間帯の重複判定、「指名なし」での別担当者への割り当て、予約確定時の再確認、取得エラー時の受付停止、参加解除後の参照停止を確認する。自動テストと実際の Google アカウントでの接続確認は区別して記録する

### Stage 7：予約が確実に残る
通信や Google 側の調子が悪くても、予約が消えない。

- 予約の保存に失敗しても、予約そのものは失われない。店主の画面にはまず「予約は保存されています」と伝わり、つながりが戻ったら自動で台帳への記録が追いつく
- 同じ予約が二重に記録されない。お客さんがボタンを押し直したり、通信がやり直しになったりしても、台帳に同じ予約が2件できない
- 終了条件：わざと接続を失敗させても予約が失われず、復旧後に台帳へ正しく1件だけ記録される

### Stage 8：言葉で直す、お知らせが届く
公開したあと、お店の変更を言葉で頼める。

- 「来月から水曜を定休日にして、新しいコースを追加して」のように頼むと、「こう変えます」という変更案が出る。了承すると反映される
- Stage 2 のペンでの依頼も、ここで本当に反映されるようになる
- 変更したら履歴（history.md）に「いつ、何を頼んで、何が変わったか」が残る。仕様書（spec.md）も今の内容に合わせておく
- 予約が入った時とキャンセルされた時に、お客さんと店主へお知らせメールが届く
- 終了条件：定休日の追加とメニューの追加を頼んで、変更案→了承→画面とシートへの反映→履歴に残る、までが通しでできる

### Stage 9：声で話す
声だけで、聞き取りからプランまで進められる。一番難しい段階。

- 店主とシステムが声で会話する。システムが声で質問し、店主が声で答えると、聞き取った内容が画面の項目にその場で現れる。揃ったらプランが画面に出る
- 声の会話が長くなっても続けられる。途中で切れても、話した内容は残っていて、続きから再開できる
- 了承は声ではしない。プランは必ず画面に出し、了承は画面で押してもらう
- 声を使いたくない時（お店が営業中で声を出しにくい、など）は、文字の会話（Stage 3）でも同じことができる。声で話した内容を、その場で文字に直して見せる読み上げ補助も用意する
- 変更の依頼も声でできる
- 終了条件：声だけで聞き取りからプランまで進める。途中で切れても続きから再開できる

### Stage 10：お知らせ、公開の仕上げ
- お店のお知らせ（ブログ）：管理メニューで記事を編集し、必要なら保存前にプレビューを見て、「保存」で本番へ反映する。貼り付けたメモやテキスト・Markdownファイルから文章案も作成できる。Googleドライブのメモのリンク入力・読み込みは設けない。原稿と公開した記事は店主のドライブに残る
- 仕組み図（Stage 1）が運営の画面に置かれ、公開のたびに今の設定で作り直されて店主のドライブに残る
- お店のページが専用のアドレス（サブドメイン）で公開される。お店独自のドメインも、持ち主であることを確認して使える
- 本番のお店を開くリンクは「公開の設定」に「公開中のお店を開く」として置く。管理画面の共通ヘッダーには表示せず、ローカルの試す画面と区別する。公開前はリンクを表示しない
- 使い方のマニュアル（実際の画面の写真付き）を用意する
- 終了条件：次の「受け入れ条件」をすべて通しで確認できる

## 本番データの個別管理と保存

- 「お店の基本情報」「メニュー・料金」「スタッフ・勤務」に個別の管理メニューを用意する。「お店の基本情報」には、店名・紹介・アクセス・通知先、営業時間・定休日・臨時休業、予約の受付・キャンセルなどのルールを同じ画面にまとめる。営業時間・休業日・予約ルールの独立したサイドバーメニューは置かない。各設定欄の保存はその対象だけを更新し、他の編集内容を上書きしない。店主だけが編集・保存でき、「保存」でその項目だけを本番に反映する。編集中には本番は変わらない
- 本番の他の項目や追加ページをマージして保持し、メニュー・スタッフの参照や予約ルールを検証してから保存する。新しいメニューは無効で追加し、スタッフの対応メニューを設定してから有効にする
- 保存元と最新のデータを比較し、競合時は編集を残して保存を止める。保存リクエストの識別子と内容をブラウザに保持し、失敗時や再読込後には同じ保存として再試行する。状態確認なしに別の保存で反映途中の処理を置き換えない
- 予約の状態変更・お問い合わせへの返信・ブログやお知らせの記事は、それぞれの既存管理メニューで扱う。ブログ・お知らせの「保存」は記事単位で本番に反映し、版番号の競合を検出する。サンプルの記事や予約とは分離する
- ユーザーが追加したページはナビゲーションと専用URLから閲覧でき、Drive に設定・HTML・仕様と履歴を残す。削除・アドレス変更の反映時は古い生成HTMLも Drive のゴミ箱へ移す

## 競合のプレビューとAI結合

- 同じ画面をローカルとリモートの両方で変更した場合は、採用を決める前にローカル／リモートの読み取り専用プレビューを並べる。片側で削除された場合も、削除と編集を比較できる
- ローカルを採用、リモートを採用、AIによる結合案、から選べる。AIには編集元・ローカル・リモートの対象画面だけを渡し、結合案と説明を返させる。ページIDの変更や対象外の設定は許可しない
- AI案はプレビューを確認して「結合案をローカルに採用」を押すまで適用しない。どの採用方法でも本番への反映は別操作とする。採用前にはリモートを再取得して比較し、更新されていれば再比較する
- 採用前のローカル・編集元・リモートはブラウザに最大20件まで控えを保存し、ローカル編集を復元できる。別ページの変更やサンプルは解決操作に含めない
- Drive の反映は選んだ画面の HTML と JSON を更新・削除し、他のページのファイルやメニュー／勤務の行は書き換えない。台帳の pages タブも1画面1行の record(JSON) として選択した行だけを更新する。settings.pages は本文を含めない索引とし、共有のページ索引・仕様書・履歴と、ダウンロード用の index.html・data.js・shop.json・mock.json の公開スナップショットを合わせて更新する

### 入力の案内と日付形式
- 初回のお店づくりでは「データと権限の仕組み」の代わりに、「こんな風にすすみます」の例を表示する。「はじめる」から「どういう業種のお店ですか？」に答え、番号付きの候補からほしい機能を選び、「それ以外に欲しいページはありますか？」に答えてから画面案に進む。機能は番号・言葉で複数選べる。この順番は例であり、AIは今回の回答と会話の文脈を考慮して必要な不明点だけを質問する。回答済みの項目や、希望の範囲が明確な場合の追加ページ確認は省き、情報が揃ったら、確認画面へ移る前に必ず「ほかに伝えたいことはありますか？」と聞く。返答を受け、追加内容も含めて情報が揃ってから画面案へ進む。文字・音声とも返答前に確認画面へ進めない。文字・書き起こしのどちらも通常のチャットに送って同じ方針を適用する。画面一覧を確認し、仮公開して試すまでを段階的に案内する。例文を入力する操作は置かない。チャットは入力エリア内に「画像を添付」「音声入力」「送信」をまとめる。「音声入力」を押したときに書き起こしを開始する。入力欄は編集可能に保ち、終了キーワードまたは停止ボタンで止める。手動送信も可能で、その際は音声認識を止めてから送信する。
- 日付の入力表示はブラウザーの言語にかかわらず `YYYY/MM/DD`、日時は `YYYY/MM/DD HH:mm` とする。予約・記事・お客様の絞り込み・サンプルデータ・臨時休業日が対象。カレンダー選択を残し、保存およびAPIのISO形式は維持する。存在しない日付は入力エラーとして表示する。

- 非ログインのお客様は「お店のこと」をトップページとして表示する。ヘッダーの下に会員登録・ログインの案内をまとめ、「初めての方」「登録済みの方」を区別する。「会員登録」「ログイン」はいずれも既存のGoogle認証へ進み、初めてのお客様は認証後に登録される。明示的な予約リンクは引き続き予約画面を開く。予約画面内には重複するログイン案内を置かず、ヘッダー下の会員登録・ログインの案内へ統一する。

- 画面の確認・本番公開は「お店のこと」から開始し、お店のメニューやリンクから画面を移動する。独立した画面選択欄は表示しない。

- 本番公開前の通常操作は「本番公開する」「修正依頼する」。「修正依頼する」で「いま開いている画面」「動作・機能」「お店の情報・登録データ」を選ぶ。画面はプレビューで現在開いている画面を選択した編集画面へ進み、記事の場合は同じ記事も引き継ぐ。動作・機能は「AIとお店をつくる」の「修正」を選択した状態へ進む。データはデータ管理へ進み、メニュー・料金・予約・記事などの専用管理メニューへの導線を開く。選択を閉じた場合はプレビューの表示と入力を維持する。変更後のプレビュー再取得は読み込み失敗・確認後の内容変更による公開拒否時にだけ案内する。

- 仮公開中の確認導線は「画面の確認・本番公開」にまとめ、「仮公開中のページを見る」は表示しない。プレビューAPIは実際の公開側の設定と公開済み記事だけを取得する。承認済みでも未反映のプラン、ブラウザー内の編集中データ、記事の下書きを表示しない。

- 変更履歴には件数と履歴だけを表示し、「history.md をダウンロード」「最新に更新」は設けない。履歴と現在のお店の設定は画面を開くと取得する。読み込み失敗時だけ再試行を案内する。

- 変更履歴は件数を添えたアコーディオンにして、初期状態は閉じる。見出しのクリックまたはキーボードで開閉し、開くと新しい順に履歴を読める。

- 仮公開中の案内右側に公開への専用枠を置き、「画面を確認して本番公開へ」を主ボタンとする。遷移先の見出しは「画面の確認・本番公開」。画面下部に追従する操作欄で公開範囲の変更を説明し、「修正依頼する」「本番公開する」を並べる。

- お問い合わせフォームはログイン中のユーザー名を自動入力し、返信先メール欄に同じGoogleアカウントのメールアドレスを表示する。返信先メールは読み取り専用で、送信・返信はサーバーが確認したログインアドレスに統一する。

### お客様の会員登録
- 現在のGoogle認証で `email_verified` を確認したあと、お店ごとに名前・生年月日・性別を登録する。性別は女性・男性・その他・回答しないから選べる。未登録の場合は予約と問い合わせの送信前に登録画面を表示し、APIでも登録を必須にする。生年月日は有効な過去または当日の日付に限定する。
- 登録した名前を予約・問い合わせへ自動入力する。マイページから会員情報を変更できる。メールはログインで確認したアドレスにひも付け、別の顧客や別のお店の会員情報を読み書きできない。
- 会員情報は店主の非公開 `customers` シートへ保存する。旧3列の台帳は既存行を保持して名前・生年月日・性別の列を追加する。プロフィールは本人向けAPIと権限のある運営者の顧客詳細だけで返し、公開設定・記事・ダウンロード用公開ページには含めない。登録しただけでまだ予約のないお客様も顧客一覧から確認できる。
- 編集プレビューの「表示」メニューは、外側のクリックとEscキーで閉じる。メニュー内の操作では閉じない。

### AIの参照用に保存する会話の文脈
- 運営画面の「AIとお店をつくる」は、相談・修正・新ページ作成のすべてをチャット形式にする。文章は送信ごとにユーザーとAIの発言を会話欄へ追加し、返答のたびに確認画面へ切り替えない。案ができたらチャット内に「変更案を確認する」を表示し、内容を確認してから明示的に反映する。
- 音声は入力欄への書き起こしとして扱い、送信した文章だけを通常のチャット経由で保存する。認識途中・未送信の下書きは会話の文脈に保存しない。AIの回答は画面で読み、読み上げや音声による双方向会話は行わない。録音ファイルは保存しない。
- チャットと発言はお店・アカウントにひも付ける。APIは本人の会話だけを列挙・読み書きし、公開APIや公開ページに含めない。会話の保存・参照は裏側で行い、履歴一覧・会話の新規作成・文脈確認などの管理UIは置かない。表示するのは現在のやりとりだけとする。
- 返答と案の生成には、現在の設定・変更履歴・現在のやりとりに加え、同じお店・同じアカウントにひも付いた過去の発言を関連語で検索して渡す。AIは必要なら追加の検索語を返して過去のやりとりを再調査できる。過去の提案を現在の事実や新しい変更依頼と混同しない。リクエストに含まれた偽の会話で保存済みの文脈を上書きしない。
- 発言は先に保存し、AIの失敗後も再試行できる。送信IDで重複を防ぎ、同じ会話の変更案も同じIDで復旧する。連携前はFirestore、連携後は非公開の `ai_chats`・`ai_chat_messages` シートへ保存する。Sheetsへの書き込みはFirestoreへ記録してから行い、中断時は再読込で同じ行へ復旧する。公開前からの会話も連携後に移し、成功後に作業用コピーを削除する。

### はじめるとAIが質問する
- 初回のお店づくりも、相談・修正・新ページ作成も「はじめる」でチャットを開く。最初の短い質問はAI側の発言として表示し、ユーザーは文章で答える。初回は業種と希望の機能だけを確認し、スタッフ・料金・営業時間はまだ必須にしない。
- 「音声入力」でモーダルを開き、話した内容を書き起こす。モーダル内の文章を編集でき、下書きはチャットの入力欄にも保持する。終了キーワードの案内と変更設定はモーダル内にだけ表示する。Escape・閉じる・下書きに戻るで音声認識を止め、未送信の文章を保持する。終了キーワードの既定値は「以上」。末尾の確定した認識結果でだけキーワードを除いて送信し、途中の言及や未確定の認識結果では送信しない。終了キーワードは変更・空欄による無効化が可能で、ブラウザに保存する。手動停止・無音終了・エラー時は送信せず下書きを保持する。入力中の手修正を古い認識結果で上書きしない。送信・画面切替・コンポーネント終了時は音声認識を停止する。画像生成やペンでの依頼ではキーワードは停止だけを行い、実行は画面で確認してから行う。
- 初回の案がまとまったら画面一覧と機能の確認へ進む。直したいことは同じ会話で続けられ、仮公開・本番公開の確認手順は維持する。
